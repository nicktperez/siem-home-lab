# Synthetic SSH Brute-Force Investigation

## Scenario

This case study uses controlled events generated by `scripts/generate_syslog.py`. It demonstrates the analyst workflow for investigating repeated SSH authentication failures without targeting a real system.

## Detection hypothesis

A single source producing five or more failed SSH authentication attempts within one minute may indicate password guessing, a misconfigured service, or an automated scanner. The threshold is intentionally simple so the data path and investigation logic remain easy to inspect.

## Evidence sources

- `syslog-*`: normalized authentication events retained for investigation
- `alerts-ssh-*`: threshold alerts created by the Logstash detection pipeline
- Kibana dashboard: alert volume, source addresses, and activity over time

## Investigation

1. Locate the alert in `alerts-ssh-*` and record its source, time window, and failure count.
2. Pivot to `syslog-*` using the same source and surrounding time range.
3. Confirm the alert is supported by at least five underlying failure events.
4. Review targeted usernames and timing to distinguish rapid automation from isolated user mistakes.
5. Search before and after the alert window for successful authentication from the same source.
6. Check whether the source is expected lab infrastructure or part of the synthetic generator.
7. Record the disposition and preserve the queries used to reach it.

## Finding

For the supplied synthetic scenario, the related events are generated intentionally and the expected disposition is **benign test activity**. The alert remains useful because it demonstrates that raw telemetry is preserved separately from the threshold result and can be used to validate why the detection fired.

## Analyst conclusion

The threshold logic is understandable and reproducible, but it is not sufficient by itself to label activity malicious. A production-quality version should add context such as asset criticality, source reputation, successful logins, user baselines, and allowlists before escalation.

## Recommended response for an equivalent real alert

- Validate the source and affected account owners.
- Review successful authentication and post-login activity.
- Temporarily block an untrusted source if attempts continue.
- Reset or protect targeted accounts when compromise is plausible.
- Preserve relevant logs and document the disposition.
- Tune the rule only after confirming repeated false positives.
